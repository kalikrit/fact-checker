# Use Cases

Сценарии использования Fact Checker. Описывают **что система умеет
делать** с точки зрения пользователя и системы, ещё без привязки
к коду.

Версия: 1.0
Дата: 2026-09-25

---

## Акторы

1. **Пользователь** — вводит текст, читает вердикт.
2. **Система** — внутренние акторы, которые «делают работу» без участия
   пользователя.
   - **Пайплайн** — оркестратор шагов.
   - **LLM** — извлечение, оценка, вердикт.
   - **Поиск** — DuckDuckGo + Wikipedia.
   - **Кэш** — хранилище повторных запросов.
   - **БД** — история проверок и статус задач.

---

## UC-1. Отправить текст на проверку

**Актор:** пользователь.
**Триггер:** нажатие кнопки «Проверить».

**Основной поток:**
1. Пользователь вводит текст (до 1000 символов).
2. Нажимает «Проверить».
3. Система валидирует вход (не пусто, не слишком длинно, не только
   пробелы).
4. Создаёт задачу (`task_id`) со статусом `pending`.
5. Возвращает `task_id` в UI.
6. UI переходит на страницу результата и начинает polling.

**Альтернативные потоки:**
- **A1.** Текст пустой → ошибка «Введите текст».
- **A2.** Текст слишком длинный → ошибка «Максимум 1000 символов».
- **A3.** Текст содержит только цифры/пунктуацию → ошибка «Введите
  осмысленный текст».

**Результат:** создана задача, UI показывает прогресс.

---

## UC-2. Получить статус задачи

**Актор:** пользователь (через UI).
**Триггер:** UI опрашивает сервер каждые 2 секунды.

**Основной поток:**
1. UI → `GET /api/check/{task_id}`.
2. Сервер возвращает статус:
   - `pending` — задача в очереди.
   - `running` — пайплайн работает, есть прогресс.
   - `completed` — результат готов.
   - `failed` — ошибка с описанием.
3. UI обновляет прогресс-бар.
4. При `completed` — UI прекращает polling и показывает результат.
5. При `failed` — UI показывает ошибку и кнопку «Повторить».

**Результат:** UI знает текущий статус и обновляет интерфейс.

---

## UC-3. Извлечь утверждения из текста

**Актор:** система (пайплайн).
**Триггер:** задача перешла в `running`.

**Основной поток:**
1. Пайплайн отправляет текст в LLM с промптом «извлеки утверждения».
2. LLM возвращает структуру:
   - `main` — 1–3 главных утверждения.
   - `attributes` — до 5 деталей каждого main.
   - `opinions` — мнения (игнорируются).
   - `entities` — сущности внутри main и attributes.
3. Пайплайн валидирует структуру (JSON-схема, непустые поля).
4. При ошибке — retry до 3 раз (Ralph Loop).
5. При успехе — сохраняет в задачу.

**Результат:** есть main + attributes + entities.

---

## UC-4. Оценить правдоподобность main

**Актор:** система.
**Триггер:** после UC-3.

**Основной поток:**
1. Для каждого main-утверждения — LLM-вызов с промптом «оцени
   правдоподобность».
2. LLM возвращает `high` / `medium` / `low` + объяснение.
3. Пайплайн сохраняет оценку.

**Результат:** для каждого main есть оценка правдоподобности.

---

## UC-5. Найти источники для main

**Актор:** система.
**Триггер:** после UC-4.

**Основной поток:**
1. Пайплайн формирует 2–3 поисковых запроса (RU + EN).
2. Для каждого запроса:
   - проверяет кэш (`search_cache`);
   - если нет — вызывает DuckDuckGo + Wikipedia;
   - сохраняет в кэш.
3. Объединяет результаты, убирает дубликаты по URL.
4. Для топ-10 URL — скачивает страницы (`page_fetcher`) и извлекает
   текст.
5. Скачивает **только те**, которых нет в `page_cache`.

**Результат:** набор источников (URL + title + snippet + domain + trust).

---

## UC-6. Оценить надёжность источников

**Актор:** система.
**Триггер:** после UC-5.

**Основной поток:**
1. Для каждого источника:
   - определяет домен;
   - проверяет по whitelist → `high` / `medium` / `low`;
   - если домен неизвестен — LLM оценивает по содержанию.
2. Сохраняет trust-уровень.

**Результат:** каждый источник имеет trust.

---

## UC-7. Извлечь доказательства из источников

**Актор:** система.
**Триггер:** после UC-6.

**Основной поток:**
1. Для каждого main — LLM-вызов: «вот текст источников, найди
   фрагменты, подтверждающие или опровергающие утверждение».
2. LLM возвращает:
   - список цитат;
   - для каждой: `supports` / `refutes` / `neutral`;
   - URL источника.
3. Пайплайн фильтрует: только `supports` и `refutes`.

**Результат:** список доказательств.

---

## UC-8. Вынести вердикт по main

**Актор:** система.
**Триггер:** после UC-7.

**Основной поток:**
1. Пайплайн собирает:
   - plausibility (UC-4);
   - evidence strength (strong/weak/none) по правилу «2+ независимых
     источника»;
   - список доказательств.
2. Применяет **матрицу вердиктов** (см. `MODEL.md`, раздел 6).
3. LLM формирует объяснение: «почему такой вердикт».
4. Сохраняет результат.

**Результат:** вердикт по main с объяснением.

---

## UC-9. Проверить атрибуты (условно)

**Актор:** система.
**Триггер:** если вердикт main ∈ `{true, mostly_true}`.

**Основной поток:**
1. Для каждого атрибута (до 5):
   - извлекает сущности (уже есть из UC-3);
   - ищет сущность в сети (1 запрос);
   - классифицирует:
     - найдено → `none`;
     - не найдено → `fabricated`;
     - найдено похожее → `distorted`;
     - контекст не совпадает (время, тип, роль) → `anachronistic` /
       `type_mismatch`;
     - маловероятно → `improbable`;
     - не удалось → `unverifiable`.
2. Сохраняет сигналы.

**Если main НЕ подтверждён:**
- UC-9 **пропускается**.
- `attributesChecked: false`.
- В выводе — «детали не проверялись».

**Результат:** сигналы атрибутов (или пропуск).

---

## UC-10. Агрегировать финальный вердикт

**Актор:** система.
**Триггер:** после UC-8 (+ UC-9, если запускался).

**Основной поток:**
1. Если атрибуты проверялись и есть `fabricated` / `distorted` /
   `anachronistic` / `type_mismatch`:
   - вердикт main понижается до `misleading`.
2. Формирует финальный `FactCheckResult`:
   - main + attributes;
   - вердикт;
   - источники;
   - объяснение;
   - дисклеймер;
   - `confidence` (0..1).
3. Сохраняет в БД.
4. Меняет статус задачи на `completed`.

**Результат:** результат готов, сохранён, доступен через API.

---

## UC-11. Показать результат пользователю

**Актор:** пользователь.
**Триггер:** статус задачи → `completed`.

**Основной поток:**
1. UI получает `FactCheckResult`.
2. Показывает:
   - вердикт (цвет + иконка + текст);
   - main-утверждение;
   - объяснение;
   - список источников с trust и цитатами;
   - проверенные атрибуты (если были);
   - дисклеймер.
3. Пользователь может кликнуть на источник → откроется в новой вкладке.

**Результат:** пользователь видит полный результат.

---

## UC-12. Просмотреть прогресс

**Актор:** пользователь.
**Триггер:** пока задача в статусе `running`.

**Основной поток:**
1. UI показывает прогресс-бар и текущий шаг:
   - «Извлечение фактов…»
   - «Оценка правдоподобности…»
   - «Поиск источников (2 из 3)…»
   - «Анализ доказательств…»
   - «Формирование вердикта…»
   - «Проверка деталей (1 из 5)…»
2. Прогресс обновляется при каждом изменении статуса.
3. UI показывает **процент** завершения и **текущий шаг**.

**Результат:** пользователь видит, что происходит, и не думает, что
система зависла.

---

## UC-13. Обработать ошибку

**Актор:** система.
**Триггер:** любой шаг пайплайна упал.

**Основной поток:**
1. Пайплайн ловит ошибку.
2. Классифицирует:
   - **transient** (сеть, таймаут LLM, rate limit) → retry до 3 раз.
   - **permanent** (невалидный JSON, ошибка схемы) → failed.
   - **unknown** → failed с логом.
3. Если retry успешен — продолжает.
4. Если нет — статус `failed`, сохраняет описание ошибки.
5. UI показывает понятное сообщение:
   - «Не удалось получить ответ от LLM. Повторите через минуту».
   - «Не удалось найти источники. Попробуйте переформулировать».
   - «Внутренняя ошибка. Мы уже разбираемся».
6. Кнопка «Повторить».

**Технические детали** (stack trace) идут в логи, **не в UI**.

**Результат:** ошибка обработана, пользователь уведомлён.

## Что НЕ входит в use cases (MVP)

- Регистрация, авторизация, аккаунты.
- Оплата, подписки.
- Загрузка файлов, изображений, видео.
- Уведомления по email.
- Комментарии, обсуждения.
- Публичный API для сторонних разработчиков.
- Экспорт результатов в PDF/CSV.

## Отложено (post-MVP)

### UC-14. Показать историю проверок

**Актор:** пользователь.
**Триггер:** переход на страницу «История».

**Основной поток:**
1. UI → `GET /api/history`.
2. Сервер возвращает последние 20 проверок.
3. UI показывает список: текст, дата, вердикт.
4. Клик по записи → детальная страница (UC-11).

**Почему отложено:** нужна БД, session-based идентификация или
авторизация, дополнительная UI-страница. Усложняет MVP.

---

### UC-15. Повторить проверку

**Актор:** пользователь.
**Триггер:** кнопка «Повторить» на странице результата.

**Основной поток:**
1. UI повторно отправляет текст.
2. Система проверяет кэш `verdict_cache`.
3. Если есть — возвращает результат мгновенно.
4. Если нет — запускает пайплайн заново.

**Почему отложено:** кэш всё равно работает на уровне API. Отдельная
кнопка «Повторить» — UX-улучшение, не критично для MVP.

---

### UC-16. Обратная связь по вердикту

**Актор:** пользователь.
**Триггер:** кнопка «Вердикт неверный» на странице результата.

**Основной поток:**
1. Пользователь отмечает, что вердикт ошибочный.
2. Опционально — комментарий.
3. Запись сохраняется в БД для анализа и улучшения.

**Почему отложено:** требует UI, БД, продумывания, как использовать
данные. Полезно, но не для MVP.

## Принятые решения

1. **UC-9 (проверка атрибутов) — условный.** Запускается только при
   `true` / `mostly_true`.
2. **История (UC-14)** — отложена в post-MVP.
3. **Повтор (UC-15)** — отложен. Кэш работает на уровне API без
   отдельной кнопки.
4. **Прогресс (UC-12)** — процент + текущий шаг, без детальных логов.
5. **Ошибки (UC-13)** — понятные сообщения без stack trace.
6. **Обратная связь (UC-16)** — не в MVP.
